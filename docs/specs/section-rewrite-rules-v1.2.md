# 正式需求文档 Section Rewrite 规则 v1.2

## 1. 目标

本文档用于定义正式需求文档的结构和写回规则，解决当前“讨论内容被直接 append 到文档末尾”的问题。

目标是让正式需求文档成为稳定、可复用、可进入后续规格层的结构化产物，而不是聊天记录附录。

## 2. 核心原则

- 正式文档是编译产物，不是聊天日志
- 写回必须按 section 定位和替换
- 重试不能产生重复内容
- 聊天过程与正式文档分离
- 正式文档结构必须稳定

## 3. 推荐文档结构

建议正式需求文档至少固定以下 section：

```markdown
# REQ-{ID} {需求名称}

## 需求概览
[系统生成的需求摘要]

## 问题描述
[结构化内容]

## 使用场景
[结构化内容]

## 输入
[结构化内容]

## 输出
[结构化内容]

## 边界
[结构化内容]

## 验收标准
[结构化内容]

## 非功能要求
[结构化内容]
```

可选扩展 section：

- `历史约束摘要`
- `当前 review 摘要`
- `附录：讨论纪要`

但这些附加 section 不应污染核心需求结构。

## 4. 写回模型

## 4.1 输入

正式文档写回模块应至少接收：

- 当前正式文档内容
- 本轮结构化 `updates`
- 目标 section 名称
- 当前 REQ 元数据

## 4.2 输出

输出应为：

- 更新后的整篇正式文档结构
- 本轮实际改写的 section 列表
- 最近一次写回时间

## 5. Section 定位规则

## 5.1 基本规则

每个 section 使用二级标题 `##` 作为稳定锚点。

例如：

- `## 问题描述`
- `## 使用场景`
- `## 输入`

某 section 的内容边界为：

- 从当前 section 标题之后开始
- 到下一个 `## ` 标题之前结束

## 5.2 定位要求

- 标题名必须精确匹配预定义 section 名称
- 若目标 section 不存在，应优先补齐标准模板而不是自由 append
- 不允许在文档末尾直接增加“本轮讨论总结”

## 6. Rewrite 规则

## 6.1 标准替换流程

每次写回时：

1. 读取当前正式文档
2. 解析标准 section 结构
3. 找到本轮要更新的 section
4. 用结构化内容替换原 section 内容
5. 保留其他 section 不变
6. 输出完整但结构稳定的正式文档

## 6.2 同轮多字段更新

如果用户一轮里补充了多个字段：

- 允许一次写回多个 section
- 每个 section 单独替换
- 不因多字段输入而退化成整段总结 append

## 6.3 未完成字段

未完成字段应保留稳定占位，例如：

- `待补充`
- `待进一步澄清`

不要因为字段暂时为空，就删除该 section。

## 7. 幂等规则

## 7.1 重试不重复

同一轮因网络重试再次写回时：

- 不应重复追加相同内容
- 不应重复生成“讨论总结”
- 不应打乱 section 顺序

## 7.2 内容相同不重复改写

若新内容与目标 section 内容一致：

- 可跳过实际写回
- 仅更新时间戳或状态

## 8. 正式文档与聊天日志分离

建议将聊天过程视为独立上下文，不直接写入正式需求文档。

如果确有需要保留过程，可单独记录为：

- 附录文档
- 讨论纪要文档
- Bitable 备注或历史记录

但正式需求文档本体必须保持简洁和结构化。

## 9. 推荐的结构化内容要求

### 9.1 问题描述

应回答：

- 现在存在什么问题
- 为什么是问题
- 不解决会造成什么影响

### 9.2 使用场景

应回答：

- 谁在什么情况下使用
- 触发条件是什么
- 期望结果是什么

### 9.3 输入

应明确：

- 输入来源
- 数据格式
- 约束条件

### 9.4 输出

应明确：

- 输出内容
- 输出格式
- 输出方式

### 9.5 边界

应明确：

- 本需求不包含什么
- 不负责什么

### 9.6 验收标准

应尽量采用：

- 数值阈值
- 布尔条件
- 明确 schema
- 错误码

避免使用模糊表达，例如：

- 更稳定
- 更方便
- 体验更好

## 10. 推荐实现方式

建议将正式文档写回实现为单独模块，例如：

- `RequirementDocumentCompiler`
- `SectionRewriteEngine`

该模块只负责：

- 生成标准文档骨架
- 按 section 定位
- 替换目标内容
- 输出稳定 markdown 或 doc block

它不负责：

- 深度需求推理
- review 判断
- 状态推进

## 11. 验收标准

- 需求讨论进行多轮后，正式文档仍保持稳定 section 结构
- 文档中不再出现聊天摘要的堆积 append
- 同轮重试不会重复写入内容
- 多字段更新可以一次性稳定写回
- 空字段仍保留标准 section 骨架
