# Harness 方法论上下文

本次开发最终目标：在新的项目里落地三层架构方案，形成一套可执行的上下文文档包，支持从现有 OpenClaw/飞书环境无缝启动实现工作。

本文档把 Harness Engineering 方法论中与“需求层新架构”直接相关的部分提炼出来，作为实现边界和设计约束。

## 1. 方法论核心结论

根据 Harness Engineering 方法论 v1.2，完整工作流由三维构成：

- 纵向流程：需求层 -> 规格层A -> 规格层B -> 生成层 -> 验证层 -> 集成层 -> 交付层
- 横向基础设施：人工协同轨（飞书 + OpenClaw）与工程自动化轨（GitHub + CI）
- 层内子流程：由 AI 在每层内部自主推进

需求层只是整条链路的入口，但必须承担一个关键责任：

> 把模糊业务意图转成结构化、可审查、可流转的需求事实。

## 2. 需求层在方法论中的定位

方法论 v1.2 中，需求层的目标是：

- 将客户描述转成经过审查的需求文档
- 用 REQ ID 贯穿飞书 -> Bitable -> GitHub 全链路
- 在飞书内闭环，不直接触碰 GitHub

原方法论把需求层划分为：

1. 需求创建
2. 需求讨论
3. UI 设计（可选）
4. 需求审查

新项目需要保留这个阶段划分，但要升级“需求讨论”的实现方式。

## 3. 新项目相对于 v1.2 的升级点

### 原 v1.2 的问题

原方案中：

- 主协调 Agent 同时承担编排和深度需求写作
- 讨论阶段更像字段补全
- review 发生得太晚
- 文档写回缺少稳定的结构化机制

### 新项目的升级方向

新项目将需求层升级为：

- 飞书工作流/自动化负责触发与基础编排
- Coordinator Service 负责规则化状态推进
- author agent 负责需求构造
- review agent 负责每轮质量把关

这使需求层从“流程演示”升级为“需求工程”。

## 4. 与上游方法论的一致性

新架构仍然满足方法论核心原则：

- REQ ID 作为跨层唯一索引
- Bitable 作为全生命周期状态机
- 需求层在飞书侧闭环
- 人工卡点保留
- 需求层输出仍然服务于后续 Spec/Harness 流程

## 5. 与上游方法论的显式差异

新项目将显式修改以下部分：

### 5.1 主协调能力下沉为 Coordinator Service

它不再作为 OpenClaw 主协调 agent 承担高质量需求构造，而是作为独立后台服务负责：

- 飞书事件入口
- 编排
- owner
- 状态机
- 文档正式写回
- 调 author/reviewer

### 5.2 需求讨论不再等于字段补全

需求讨论阶段的真正目标是：

- 澄清问题本质
- 明确场景
- 约束边界
- 量化验收标准
- 形成“高质量需求方案”

字段只是文档输出的承载形式，不是讨论本身。

### 5.3 review 从阶段末尾前移到每轮

从：

- 写完后统一 review

变成：

- author 写一轮
- review 审一轮
- 不满意继续打磨

### 5.4 飞书自动化成为编排层的一部分

飞书工作流/自动化用于：

- 触发器
- 条件分支
- 通知
- 调 HTTP/Webhook
- 驱动部分基础状态推进

## 6. 新项目必须满足的方法论约束

新实现必须继续满足：

- REQ ID 格式：`REQ-{PROJECT}-{NNN}`
- 全生命周期 Bitable
- 需求层输出可进入规格层
- 状态机可审计
- 人工确认点不可绕过
- 所有重要写入具有幂等性和可恢复性

## 7. 对实现最有价值的判断

如果只保留“主 agent + 字段填补”，那只是方法论外观上的完成，不是内容质量上的完成。

新项目真正要补的，不是更多字段，而是：

- 显式接手
- 多轮构造
- 每轮 review
- 结构化文档编译
- 飞书自动化 + Bot 编排分层
